# 决策记录

记录实现和最初设计不同的地方。每条写明当时的选择、原因和代价，方便以后重新评估。

## 1. 手机应用是新写的 Expo 应用

**选择：** `apps/mobile` 从空白的 Expo SDK 58 工程写起，没有在已有的手机工程上改。

**原因：** 手机只做遥控器和审批器，页面少；直接对接本仓库的 tRPC 手机路由和 better-auth，
不需要先拆掉另一套数据层。

**代价：** 没有现成的对话输入框、语音输入、微信登录和热更新，这些要另做。

## 2. 微信共享机器人用服务号

**选择：** 共享机器人接微信公众平台的服务号（客服消息接口），没有用每个用户扫码授权、
每人一条长连接的方式。每个 Agent 自己配置的微信渠道（iLink）仍然保留。

**原因：** 服务号是官方接口；服务端不用为每个用户维持连接，也不用按用户分片。

**代价：**

- 需要认证过的服务号。
- 用户 48 小时没有给服务号发消息，服务号就不能主动发消息给他。超过这个时间的提醒只能靠手机推送。
- 用户看不到昵称，只有一个不透明的 openid。

## 3. iMessage 只接了一家线路供应商

**选择：** 共享的 iMessage 线路只接了 Linq。

**原因：** 它有官方的 Chat SDK 适配器，接入成本最低。

**代价：** 没有备用线路。等实测 Linq 的送达率和限制后，再决定第二家或自建兜底。只支持一对一聊天。

## 4. 国内版套餐是预付，不自动续费

**选择：** 微信支付和支付宝按月或按年预付，到期后用户再买一次。

**原因：** 自动扣款需要向微信支付和支付宝单独申请签约能力。

**代价：** 到期不会自动续上，需要到期提醒。同档再买会顺延；买更高档立即生效并替换剩余时间；
更高档还在有效期内时不能买更低档。

## 5. 待定：后台运行怎么请手机审批

**现状：** 网页端和聊天机器人启动的运行，遇到需要审批的工具会暂停，并推送到手机。
通过 API 启动、定时任务和例行任务启动的运行是 "无人值守" 模式：只标了 "需要审批" 的工具会直接执行；
策略引擎里 "始终需要审批" 的第三方操作（发送、付款、删除等）会被拒绝，而不是暂停等人。

**问题：** Biber 的手机就是审批器，后台运行本可以暂停并请手机审批，现在做不到。这是本地冒烟测试时发现的。

**待决定：** 增加一种后台审批模式：用户登记过手机或审批渠道时，后台运行遇到需要审批的工具就暂停并推送，
设定的时间内没人处理再按拒绝处理。实现排在第二步 "合上产品闭环"。

## 6. 待定：微信绑定时用户认不出是不是自己的微信

**现状：** 绑定流程是：机器人把绑定链接发给关注者，关注者在已登录的浏览器里打开并点 "确认"。
Telegram 和 iMessage 的确认页会显示用户名或手机号；微信只给一个看不出含义的 openid，确认页只能显示缩写。

**风险：** 有人可以把**他自己**收到的绑定链接转给别人，骗对方点确认。对方确认后，这个人的微信就绑到了
对方的 Biber 账号上，可以用微信指挥对方的助理。需要对方配合点击，属于社会工程，但确认页上没有可供辨认的信息。

**打算：** 微信改成反向确认：网页上点确认后显示一个短码，用户要在微信里把短码发给服务号，绑定才生效。
这样能证明确认网页的人和发微信的人是同一个人。排在第二步。
