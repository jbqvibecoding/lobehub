# 决策记录

记录实现和最初设计不同的地方。每条写明当时的选择、原因和代价，方便以后重新评估。

## 1. 手机应用是新写的 Expo 应用

**选择：** `apps/mobile` 从空白的 Expo SDK 58 工程写起，没有在已有的手机工程上改。

**原因：** 手机只做遥控器和审批器，页面少；直接对接本仓库的 tRPC 手机路由和 better-auth，
不需要先拆掉另一套数据层。

**代价：** 没有现成的对话输入框、语音输入、微信登录和热更新，这些要另做。

## 2. 微信共享机器人用服务号

**选择：** 共享机器人接微信公众平台的服务号（客服消息接口），没有用每个用户扫码授权、
每人一条长连接的方式。每个 Agent 自己配置的微信渠道（iLink）仍然保留。

**原因：** 服务号是官方接口；服务端不用为每个用户维持连接，也不用按用户分片。

**代价：**

- 需要认证过的服务号。
- 用户 48 小时没有给服务号发消息，服务号就不能主动发消息给他。超过这个时间的提醒只能靠手机推送。
- 用户看不到昵称，只有一个不透明的 openid。

## 3. iMessage 只接了一家线路供应商

**选择：** 共享的 iMessage 线路只接了 Linq。

**原因：** 它有官方的 Chat SDK 适配器，接入成本最低。

**代价：** 没有备用线路。等实测 Linq 的送达率和限制后，再决定第二家或自建兜底。只支持一对一聊天。

## 4. 国内版套餐是预付，不自动续费

**选择：** 微信支付和支付宝按月或按年预付，到期后用户再买一次。

**原因：** 自动扣款需要向微信支付和支付宝单独申请签约能力。

**代价：** 到期不会自动续上，需要到期提醒。同档再买会顺延；买更高档立即生效并替换剩余时间；
更高档还在有效期内时不能买更低档。

## 5. 后台运行请手机审批

**背景：** 网页端和聊天机器人启动的运行，遇到需要审批的工具会暂停，并推送到手机。聊天机器人在队列模式和
本地模式（`AGENT_RUNTIME_MODE=local`，国内区可选）下都是这样：本地模式原先是 "无人值守"，Telegram 模拟器
发现后已修正。通过 API 启动、定时任务和例行任务启动的运行原先一律 "无人值守"：只标了 "需要审批" 的工具
（比如在云电脑上运行代码）会直接执行；策略引擎里 "始终需要审批" 的第三方操作（发送、付款、删除等）会被拒绝，
而不是暂停等人。Biber 的手机就是审批器，所以后台运行应当暂停并请手机审批。

**决定：** 没人盯着的运行，按用户有没有登记手机分两种：

- **登记了手机：** 按用户在聊天里保存的审批方式（默认 "逐个审批"），需要审批的工具会暂停运行并推送到手机。
  "始终允许" 名单里的工具照常直接执行。
- **没有登记手机：** 和原来一样无人值守，因为没有人可以问。

适用范围：

- 任务的每一次运行（手动、按计划、心跳）；
- 服务端之间启动运行的 `POST /api/agent`；
- 调用 `aiAgent.execAgent` 时没有说明审批方式的调用方（开放 API、脚本，以及去掉 `--headless` 的 CLI）。
  网页端和手机每次都会说明审批方式，不受影响。

评测、核验、子 Agent 委派、自我迭代这类内部运行仍是无人值守。

**等待期间：**

- 任务的这一轮运行保持 "运行中"，所以按计划的下一次触发会跳过它，不会叠加运行。
- 手机上的回答会恢复运行。恢复后的运行带着任务的完成回调，结束时照常结算任务（交接、复核、下一次排期），
  "停止任务" 停的也是恢复后的这次运行。
- 一个请求等了 24 小时还没人回答，就按拒绝处理：Agent 会被告知 "没人及时回答，操作没有执行" 并继续，
  任务也随之结算。由 cron 调 `GET /api/agent/approvals/expire`，见运维手册。
- 只对后台运行的请求这样处理，也就是会话的 `trigger` 为 `task`、`cron`、`api`、`openapi` 或 `cli`。
  聊天里的请求一直等用户回答。

**已知限制：**

- 设置了 `heartbeatTimeout` 的任务（默认不设）可能在等待期间被判为超时。
- 调用 `aiAgent.execAgent` 时既不说明审批方式、也不传 `trigger` 的调用方，会话记为 `chat`。这类请求会暂停
  并推送，但不会自动过期，和聊天里的请求一样等用户回答。

## 6. 待定：微信绑定时用户认不出是不是自己的微信

**现状：** 绑定流程是：机器人把绑定链接发给关注者，关注者在已登录的浏览器里打开并点 "确认"。
Telegram 和 iMessage 的确认页会显示用户名或手机号；微信只给一个看不出含义的 openid，确认页只能显示缩写。

**风险：** 有人可以把**他自己**收到的绑定链接转给别人，骗对方点确认。对方确认后，这个人的微信就绑到了
对方的 Biber 账号上，可以用微信指挥对方的助理。需要对方配合点击，属于社会工程，但确认页上没有可供辨认的信息。

**打算：** 微信改成反向确认：网页上点确认后显示一个短码，用户要在微信里把短码发给服务号，绑定才生效。
这样能证明确认网页的人和发微信的人是同一个人。排在第二步。

## 7. 云电脑按用户隔离，不沿用 OpenBot 的共享令牌

**背景：** 云电脑的代码来自 OpenBot。OpenBot 面向单个主人，所有电脑共用一个令牌（`COMPUTER_TOKEN`），
电脑接受任何 bot id 的请求。Biber 把它用成了多租户：每个用户一台，都在同一个 `lobe-computers` 网络里。
命令在电脑里以 root 运行，读得到这个共享令牌，所以一个用户能在别人的电脑上执行命令。

**选择：** 每台电脑只拿到用部署密钥和自己 id 算出的令牌（HMAC），服务端用同样的方法算出令牌来调用；
supervisor 启动的电脑只接受自己的 bot id。读到自己电脑的令牌，也进不了别人的电脑。

**代价：** 和 OpenBot 原版多了一处不同（记在 `apps/computer/README.md`），从上游合并 OpenBot 的改动时要保留。
电脑之间仍在同一个网络里，能互相探测到 `/health`；如果以后要把命令改成非 root 运行，或把电脑分到各自的网络，
在这条下面补记。

**同一次安全评审修复的其他问题：**

- 国内版短信登录：别人能先用邮箱注册并填上机主的手机号，机主之后用短信登录会进入那个账号。
  现在只有短信验证本身建账号时能带手机号。
- 苹果订阅：漏收苹果的过期通知时，权益会一直有效；沙盒（TestFlight）购买也算数。
  现在过期一小时后不再有效，沙盒购买只对名单内的审核账号算数。
- iMessage 线路只接 iMessage，不接可伪造发送号码的短信。
